================================================================================
GENUC — PARTIE 2 : ARCHITECTURE BACKEND (Spring Boot) — VERSION APPROFONDIE
================================================================================
Chiffres bruts (genuc-backend/src/main/java/cd/genuc/) : 105 contrôleurs,
110 services, 128 repositories, 141 fichiers sous model/ (entités JPA +
enums), 45 DTO.

Couches classiques : Controller → Service → Repository → Base de données.
RÉPONSES REST — mise à jour 2026-07-16 : la classe cd.genuc.dto.
ApiResponse<T> existe désormais (créée ce jour, elle n'existait PAS
malgré ce qu'affirmait CLAUDE.md). GlobalExceptionHandler (situé dans
config/, pas dans exception/) l'utilise pour TOUTES les erreurs :
{ success:false, code, message i18n, status, timestamp, erreurs? } —
mêmes clés qu'historiquement + champ additif « success ». Les endpoints
EXISTANTS renvoient encore des ResponseEntity<?> avec DTO/Map ad hoc
(le frontend consomme ces formes) ; les NOUVEAUX endpoints doivent
renvoyer ApiResponse.ok(data). Détail du contrat en partie 10 §1.2.

CHEMINEMENT D'UNE REQUÊTE (pour se repérer dans les packages) :
  1. RateLimitFilter (security/) — compteur Redis par IP/route ; 429 si
     dépassement ;
  2. JwtAuthFilter (security/) — extrait le Bearer token, le valide via
     JwtService, peuple le SecurityContext ;
  3. règles d'URL de SecurityConfig (config/) puis @PreAuthorize de la
     méthode — 401/403 si échec ;
  4. contrôleur (controller/) — parse/valide (@Valid) et délègue ;
  5. service (service/) — logique métier, transactions, cache, événements ;
  6. repository (repository/) — Spring Data JPA vers PostgreSQL (routé
     lecture/écriture par RoutingDataSource) ;
  7. toute exception remonte au GlobalExceptionHandler qui la formate.

2. PATTERNS ARCHITECTURAUX, EXPLIQUÉS
--------------------------------------------------------------------------------
STRATÉGIE (paiement) : PaymentOrchestratorService construit une
  Transaction persistée puis délègue l'initiation à l'implémentation de
  l'opérateur choisi (Vodacom M-Pesa, Orange Money, Airtel Money,
  AfriMoney, Stripe). Intérêt : ajouter un opérateur = une classe de
  stratégie + ses métadonnées config/payment/, sans toucher au flux
  commun (création, suivi, réconciliation). Le retour se fait par WEBHOOK
  asynchrone — l'état d'une transaction n'est jamais « confirmé » dans la
  requête HTTP initiale. Détail en partie 06.

ROUTAGE LECTURE/ÉCRITURE : RoutingDataSource étend
  AbstractRoutingDataSource — à chaque acquisition de connexion, une clé
  de contexte décide du pool cible : écritures → primaire, lectures →
  réplica. En dev les deux pools pointent sur la MÊME base (le routage est
  transparent) ; en prod il permet de décharger les rapports/consultations
  sur un réplica Postgres. Piège associé : une méthode de service marquée
  lecture seule qui ÉCRIT échouera ou écrira au mauvais endroit — marquer
  correctement les transactions.

ÉVÉNEMENTIEL KAFKA : @EnableKafka + paires producteur/consommateur
  (notifications, webhooks paiement, PDF). Le producteur publie un
  événement typé (dto/kafka/) et répond immédiatement ; le consommateur
  traite en tâche de fond. DÉSACTIVÉ par défaut en dev (KAFKA_ENABLED=
  false) : le code bascule alors sur exécution directe — c'est pourquoi le
  poste de dev n'a pas besoin de broker. En prod, le compose fournit
  kafka + zookeeper.

TÂCHES PLANIFIÉES : @EnableScheduling sur la classe principale ; les crons
  vivent dans les services concernés (§6) — pas de scheduler central.

CACHE : @EnableCaching + deux niveaux — Caffeine en mémoire (L1) devant Redis
  (L2). Tout est déclaré dans cd.genuc.config.cache.CacheNames : nom, TTL et
  éligibilité au L1, un seul fichier à modifier. @Cacheable/@CacheEvict dans
  DeliberationService, EtudiantService, FiliereDetailsService,
  HoraireService, NoteService, ParametresUniversiteService,
  UniversiteService, TachPayAdminService/TachPayPaiementService.

  - Le L1 n'est activé que pour les données de RÉFÉRENCE non nominatives
    (universités, paramètres, filières, horaires). Jamais pour les notes, les
    profils ni le financier. Les invalidations sont diffusées entre instances
    par Redis pub/sub (canal genuc:cache:invalidation) ; un TTL local plafonné
    à 120 s borne l'obsolescence si un message se perd.
    Interrupteur : genuc.cache.local.enabled=false → retour à « Redis seul ».
  - Le gestionnaire refuse de créer un cache non déclaré
    (disableCreateOnMissingCache) : une faute de frappe dans un @Cacheable
    échoue au lieu de créer un cache fantôme. DeclarationCachesTest vérifie au
    build que tous les noms annotés existent dans CacheNames.
  - Sérialisation : liste blanche de types (BasicPolymorphicTypeValidator sur
    cd.genuc.*, java.util/time/lang/math). L'ancien LaissezFaireSubTypeValidator
    permettait à quiconque pouvait écrire dans Redis de faire instancier
    n'importe quelle classe du classpath. ModuleJacksonHibernate convertit les
    collections et proxies Hibernate en types java.util : sans lui, le @class
    écrit pointait sur PersistentBag et AUCUNE lecture de cache ne réussissait.
  - Supervision : GET /api/admin/cache (SUPER_ADMIN) — TTL, taux de succès du
    L1 ; DELETE /api/admin/cache[/{nom}] pour purger. Métrique d'erreurs :
    genuc_cache_errors_total.

  Règle d'or : toute mutation d'une donnée cachée doit porter le
  @CacheEvict correspondant, sinon l'API sert du périmé — en
  cas de donnée « fantôme » en dev, vider Redis (docker exec genuc-redis
  redis-cli FLUSHALL) avant de chercher un bug applicatif.
  Piège classique : @CacheEvict ne se déclenche PAS sur un appel interne à la
  même classe (auto-invocation, le proxy Spring n'est pas traversé) — c'est la
  raison des évictions globales sur NoteService.saisirEnLot/publierParCours.

CACHE HTTP : HttpCacheConfig pose no-store sur tout /api/** par défaut (une
  réponse authentifiée ne doit pas rester dans le cache disque d'un poste
  partagé) et public/max-age=60 + ETag sur la liste blanche des ressources
  publiques de référence.

@Async : un seul usage identifié — DeliberationService (traitement de
  délibération en tâche de fond, motif job + polling côté API : partie 10
  §9.2).

BUILDER : Lombok @Builder massif sur entités et DTO — les constructions
  s'écrivent Entite.builder().champ(x).build().

4. CONFIGURATION — OÙ SE RÈGLE QUOI
--------------------------------------------------------------------------------
application.yml — configuration de RÉFÉRENCE, indépendante du profil.
  Convention systématique ${VARIABLE:defaut} : chaque réglage est
  surchargeable par variable d'environnement sans toucher au fichier.
  Contenu notable : pool Hikari (100 connexions primaire / 50 replica),
  Flyway (désactivé par défaut — voir partie 12 §5b), cache Redis TTL
  3600s, SMTP, Thymeleaf, Kafka (désactivé par défaut), secret/expiration
  JWT + refresh, secrets de signature webhook PAR OPÉRATEUR, comptes de
  test (externalisés), endpoints sandbox mobile money, Actuator/
  Prometheus/OTel, logs structurés trace/span ID.
application-dev.properties (98 lignes) / application-prod.properties
  (69 lignes) — surcharges par environnement. Prod : flyway.enabled=true
  + ddl-auto=validate (le schéma est verrouillé par les migrations).
db/migration/ — scripts Flyway V1..V7 (V1 = baseline 132 tables), voir
  partie 04.
messages_fr.properties — bundle i18n (français uniquement pour l'instant ;
  les messages d'erreur du GlobalExceptionHandler viennent de là).
Templates/ — 3 templates Thymeleaf (emails, lettre d'admission).
static/ — build React de production pré-compilé, servi par Spring Boot —
  l'alternative same-origin au reverse proxy Nginx (§2 de la partie 01).

DÉTAIL IMPORTANT — open-in-view : laissé à true (défaut Spring). Cela
garde la session Hibernate ouverte pendant TOUT le rendu de la réponse,
ce qui permet à la sérialisation Jackson de déclencher des chargements
lazy. NoteController, CoursController, InscriptionController et
UniversiteController renvoient encore des entités JPA BRUTES avec
associations lazy : désactiver open-in-view aujourd'hui provoquerait des
LazyInitializationException sur ces endpoints. La sortie propre est de
migrer ces retours vers des DTO explicites AVANT de couper open-in-view
(migration non commencée). D'ici là : open-in-view=true est un choix
contraint, pas une préférence.


5. RÔLES ET AUTORISATION
--------------------------------------------------------------------------------
15+ rôles (RoleEnum). Autorisation en deux étages : règles d'URL dans
SecurityConfig + @PreAuthorize sur les méthodes (tableau complet en
partie 10 §2 ; le code n'utilise PAS @Secured malgré CLAUDE.md).

MÉCANIQUE DU PRÉFIXE ROLE_ (source d'un bug historique) : hasRole("X")
compare avec l'authority « ROLE_X » (préfixe ajouté automatiquement),
alors que hasAnyAuthority("X") compare LITTÉRALEMENT avec « X ». Comme
JwtService produit des authorities préfixées ROLE_ (vérifié par test),
un contrôleur écrit avec hasAnyAuthority('ETUDIANT') ne matche JAMAIS —
PresenceController a eu ce bug. Règle : toujours hasRole/hasAnyRole, ou
hasAuthority('ROLE_X') si on tient à la forme longue.
Voir 05-authentification-securite.txt pour le détail complet.


6. TÂCHES PLANIFIÉES (@Scheduled) — QUI TOURNE QUAND, ET POURQUOI
--------------------------------------------------------------------------------
  job/TransactionTimeoutJob          toutes les 60 s + passe de 2 min :
      expire les transactions de paiement restées « en attente » (un
      mobile money non confirmé ne doit pas bloquer un frais
      indéfiniment) ; c'est le filet de sécurité complémentaire des
      webhooks et de la réconciliation.
  service/MetricsScheduler           toutes les 60 s : rafraîchit les
      métriques métier exposées à Prometheus.
  service/PalmaresService            02h00 : recalcul du palmarès si
      autoGeneration est activé (classements par promotion/université).
  service/ScheduledAlerteService     08h00 : génération/diffusion des
      alertes du jour (échéances, événements).
  service/ScheduledPenaliteService   minuit : applique les pénalités de
      retard de paiement sur les échéances dépassées.
  security/RefreshTokenService       03h00 : purge des refresh tokens
      expirés (la table ne grossit pas indéfiniment).
  model/ScheduledTasks               contient des crons (08h00, minuit,
      02h00) explicitement DÉSACTIVÉS en commentaire — doublons
      historiques des tâches ci-dessus, laissés en l'état pour éviter une
      double exécution. Ne pas les réactiver sans supprimer l'équivalent.
  NOTE d'exploitation : @Scheduled s'exécute dans CHAQUE instance — si le
  backend est un jour répliqué en plusieurs pods, ces tâches tourneront
  en double (prévoir un verrou type ShedLock à ce moment-là).


7. TESTS (SYNTHÈSE — le détail complet est en partie 11)
--------------------------------------------------------------------------------
13 classes, 84 méthodes @Test, concentrées sur auth/sécurité et cinq
services critiques. Points exacts à retenir :
  - la majorité sont des tests unitaires Mockito ; seuls AuthControllerTest
    et SecurityConfigTest chargent un contexte @SpringBootTest — et comme

    partie 11 §3) ;

    vraie que pour lui ;

  - JaCoCo : rapport généré à chaque mvn test (target/site/jacoco/), mais
    le SEUIL de 70 % est lié à la phase verify que les commandes
    documentées n'atteignent jamais — contrainte théorique (partie 11 §4).
